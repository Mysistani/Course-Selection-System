## مشکلات و اصلاحات

۱. section_limits قبلاً اجازه مجموعه جایگاه متفاوت برای یک دیتاست می‌داد. اکنون مقدار ناسازگار رد می‌شود. مجموعه مرجع با تابع مشترک برای builder و validator از floor(Demand/MinSectionSize) به‌دست می‌آید. آرگومان قدیمی حذف نشده ولی فقط مقادیر برابر با سقف مرجع را می‌پذیرد.

۲. validator قبلاً جایگاه مفقود/اضافی یا تغییر درسِ جایگاه به یک درس موجود دیگر را تشخیص نمی‌داد. اکنون این موارد، section_id تکراری و تفاوت کلید دیکشنری و section_id گزارش می‌شوند. گروه غیرفعال فقط بدون منابع/جلسات مجاز است. برای تقاضای صفر یا زیر حداقل هیچ جایگاه مرجعی وجود ندارد، ولی همه درخواست‌ها با None حفظ می‌شوند.

۳. loader از قبل درخواست‌ها را پیش از خروجی مدل از نظر کلید مرکب بررسی می‌کرد. پیام اکنون اختصاصی‌تر شده و سطر اولین و دومین درخواست را مشخص می‌کند؛ تفاوت Priority تکرار کلید را مجاز نمی‌کند. builder نیز Dataset ساخته‌شده دستی را قبل از ساخت Dictionary بررسی می‌کند تا درخواست تکراری بی‌صدا حذف نشود. تشخیص تکرار در validate_structure مربوط به ورودی Dataset خطادار است و با ValueError روشن متوقف می‌شود؛ لیست StructureIssue برای خود کروموزوم است.

۴. cache با None آغاز می‌شود. ورودی نگاشت‌ها کپی و ذخیره داخلی و نماهای عمومی فقط‌خواندنی هستند. ژن‌ها و زوج جلسات تغییرناپذیرند و شناسه منبع تغییرپذیر پذیرفته نمی‌شود. replace_section و assign پس از کنترل پیش‌شرط‌ها و پیش از تغییر نمره را پاک می‌کنند. unassign و deactivate از همین مسیر می‌گذرند. clone داده مستقل و نمره None دارد. شکست ویرایش، داده یا نمره را عوض نمی‌کند. دورزدن عمدی API خصوصی پایتون در قرارداد پشتیبانی نیست.

۵. IsAllowed=False قبلاً در validate_structure رد می‌شد؛ اکنون فقط ناشناخته بودن Slot خطای ساختاری است. تداخل‌ها، ظرفیت/حداقل نفر، صلاحیت استاد، نوع/تجهیزات اتاق، ممنوعیت زمان، سقف بار و حدود واحد در این تابع بررسی نمی‌شوند. اعتبار ساختاری به معنی H=0 نیست.

پوشش: مرزهای تقاضای ۰،۷،۸،۱۵،۱۶،۲۳،۲۴؛ مجموعه یکسان جایگاه‌ها؛ جایگاه اضافه/مفقود/تکراری/تغییردرس؛ پاک بودن گروه غیرفعال؛ درخواست تکراری در فایل و Dataset دستی؛ تخصیص ناموجود، غیرفعال، درس اشتباه و درخواست مفقود؛ جلسه کم، تکراری و ناشناخته؛ عدم ارزیابی قواعد سخت در validator؛ کپی مستقل، کپی ورودی، منع تغییر نگاشت‌ها و ژن‌ها، invalidate صریح و خودکار، unassign/deactivate، ویرایش ردشده و امتیاز غیرمجاز.

فایل داده جاری هنگام آزمون قفل بود و خواندن مستقیم PermissionError داد. نسخه آزمون صریحاً از snapshot بسته انتقال انتخاب و SHA-256 آن پیش از اجرا بررسی شد:


این نتیجه مربوط به نسخه مبناست و تأیید تغییرات احتمالی ذخیره‌نشده در فایل باز نیست. فایل اصلی و Excel تغییر نکردند. آزمون‌ها فایل‌های موقت خود را داخل outputs می‌سازند و پاک می‌کنند. بدون متغیر SCHEDULER_TEST_DATASET، فرمان unittest فایل جاری data را بررسی می‌کند؛ fallback مخفی وجود ندارد.

## تصمیم‌های معماری باز برای Software Architect

- API اتمی آینده برای بازتوزیع چند تخصیص و فعال/غیرفعال‌سازی گروه در Split/Merge: متدهای پایه فعلی تضمین transaction چندویرایشی ندارند. صحت ساختاری پس از تکمیل تغییرات کنترل می‌شود. در این فاز عملگر یا قرارداد transaction جدید ساخته نشد.
- اتصال cache به نسخه دیتاست و نسخه سیاست و نحوه پذیرش نتیجه ارزیابی هم‌زمان: فعلاً نمره وابسته به تغییرات خود کروموزوم است؛ تغییر context ارزیابی باید صریحاً invalidate شود. قبل از ارزیاب موازی/قابل تعویض، binding یا revision باید توسط معمار مشخص شود. اکنون اجرای موازی و Fitness وجود ندارند.
- اطلاعات تجهیزات لازم برای هر درس در Excel فعلی ستون مستقل ندارد. مدل و محل تأمین این داده قبل از قید تجهیزات باید مشخص شود؛ ساختار Excel در این فاز عوض نشد.
- MinHours، وزن‌دهی نهایی Fitness و نحوه شمارش نقض‌ها همچنان قراردادهای مرحله ارزیاب‌اند؛ این فاز آن‌ها را تصویب یا پیاده نکرد.

مجموعه مرجع جایگاه‌ها به داده همان اجرا وابسته است. اگر درخواست‌ها یا MinSectionSize تغییر کند، دیتاست جدید محسوب می‌شود و باید کروموزوم‌های جدید ساخته شوند؛ انتقال جواب قدیمی میان دو دیتاست به قرارداد جدا نیاز دارد.

## آمادگی برای Population Initialization

**از نظر ساختمان داده و قرارداد ساختاری، بله.** سازنده تکرارپذیر، جایگاه ثابت، درخواست‌های کامل با None، کپی مستقل و cache ایمن در مسیرهای API موجود فراهم است. آماده‌بودن ساختمان داده به معنی وجود Population Initialization یا اعتبار زمان‌بندی نیست. پیش از سنجش کیفیت جمعیت، HardConstraintEvaluator لازم است؛ برای مراحل عملگرها نیز تصمیم transaction و binding ارزیابی باید روشن شود.
