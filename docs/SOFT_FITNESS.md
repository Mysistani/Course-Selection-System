# Phase 3 — EvaluationContext و Soft Fitness

## تصمیم‌های جاری و تقدم آن‌ها

مبنای این فاز، تصمیم نهایی Software Architect درباره exact بودن روزهای حضور، مازاد فاصله ۳۰ دقیقه، استاد غیرفعال، دشواری حداقل ۴ و Willingness متناسب با زمان تدریس است. پس از آن، کاربر در پاسخ جدید گزینه «پوشش درخواست ضریب کل رضایت باشد» را انتخاب کرد. طبق تقدم دستور جدید، **پیش‌فرض اجرایی coverage_product است**؛ میانگین سه‌گانه قبلی تنها با نام صریح equal_components قابل انتخاب برای مقایسه است و پیش‌فرض نیست.

Policy جاری `phase3-soft-v1` این قراردادها را ثبت می‌کند. تغییر تنظیمات، fingerprint سیاست را تغییر می‌دهد و به Context/اجرای جدید نیاز دارد. فرمول‌های آزمایشی زیر قانون بهینه جهانی یا نتیجه آزمایش GA معرفی نمی‌شوند.

## API و استفاده صحیح در یک اجرا

```python
from scheduler.evaluation_context import EvaluationContext
from scheduler.constraints import evaluate_hard_constraints
from scheduler.soft_fitness import evaluate_soft_fitness
from scheduler.fitness import evaluate_fitness

context = EvaluationContext.from_dataset(dataset)  # فقط یک‌بار پیش از حلقه
hard = evaluate_hard_constraints(chromosome, context)
soft = evaluate_soft_fitness(chromosome, context)
result = evaluate_fitness(chromosome, context)
key = result.comparison_key  # (HardPenalty, -SoftScore)، کوچک‌تر بهتر است
```

API دوآرگومانی قبلی Hard، یعنی evaluate_hard_constraints(chromosome,dataset)، حفظ شده و نتیجه سازگار می‌دهد. فراخوانی‌های مکرر با همان Dataset و Policy از cache ضعیفِ هویتی Context استفاده می‌کنند؛ محاسبه fingerprint یا اسکن‌های ثابت داده در هر ارزیابی تکرار نمی‌شود. شکل صریح نیز پشتیبانی می‌شود: `evaluate_hard_constraints(chromosome,dataset,context=context)`؛ اگر Dataset به Context تعلق نداشته باشد خطا صادر می‌شود. Soft همین قرارداد ورودی را دارد؛ ارزیابی ترکیبی فقط Context می‌پذیرد.

Context یک snapshot تغییرناپذیر از Dataset و Policy نگه می‌دارد. خود Dataset نیز در ساخت، ظرف‌های ورودی را به نگاشت فقط‌خواندنی و tuple تبدیل می‌کند تا تغییر لیست یا Dictionary بیرونی اطلاعات اجرا را عوض نکند. ردیف‌های مدل از قبل frozen بودند. Policy و همه نگاشت‌ها و مجموعه‌های Context ثابت‌اند. تغییر داده/سیاست با dataclasses.replace نسخه جدید می‌سازد و اجرای جدید محسوب می‌شود. تبدیل Context به اجرای دیگر یا مخلوط‌کردن/مقایسه نتایج دو fingerprint متفاوت رد می‌شود. GA Runner هنوز وجود ندارد؛ قرارداد Runner آینده این است که یک Context را پیش از شروع بسازد و تا پایان نگه دارد. cache قدیمی خود Chromosome در این API خوانده یا نوشته نمی‌شود.

Context شامل تقاضا، همه درخواست‌ها و Priority کل، جایگاه‌های ثابت، صلاحیت‌ها، فضاهای سازگار و ظرفیت مؤثر هر زوج درس/فضا، دقیقه حداقل/حداکثر استاد، بازه‌های Unavailable، Preferredهای نرمال‌شده، ترجیحات افراد، Willingness، درس‌های دشوار و مخرج نرمال‌سازی هر دانشجو، تقویم و کران فاصله و Diagnostics ثابت است. شمار اعضا، حضورها، واحدها، بار واقعی و کسری MinHours به خود جواب وابسته‌اند و هنگام ارزیابی محاسبه می‌شوند. کسری MinHours به Diagnostics پویای Hard اضافه می‌شود و همچنان هیچ جریمه Hard یا Soft ندارد.

cache هویتی، Dataset اصلی را زنده نگه نمی‌دارد؛ با آزادشدن منبع، مدخل آن حذف می‌شود. Context نگه‌داشته‌شده برای اجرا همچنان snapshot خودش را دارد. برای استفاده موازی آینده Context باید پیش از آغاز workerها ساخته و بین آن‌ها فقط‌خواندنی به اشتراک گذاشته شود؛ این فاز Runner یا اجرای موازی نمی‌سازد.

## فرمول‌ها و مثال‌های دقیق

| مؤلفه | فرمول اجرایی | نمونه |
|---|---|---|
| RequestCoverage | مجموع Priority درخواست‌های تخصیص‌یافته / Priority همه درخواست‌های ورودی | ۷ از ۱۰ → ۰٫۷ |
| PreferredTeachingDays | max(0,1−abs(actual_days−Target)/calendar_days) | ۳ روز واقعی، هدف ۲، تقویم ۵ روز → ۰٫۸ |
| MinimizeGaps | max(0,1−excess_gap_minutes/gap_normalizer) | فاصله ۳۰ → مازاد صفر؛ ۳۱ → مازاد ۱ و در تقویم فعلی ۱−۱/۲۲۵۰ |
| PreferredTimeSlots | میانگین مطلوبیت Slotهای واقعی شخص؛ Preferred.Weight/10 و نبود Preferred برابر neutral_time_score | وزن محلی ۸ → ۰٫۸؛ بدون Preferred → ۰٫۵ |
| SpreadDifficultCourses | max(0,1−sum_day(max(0,distinct_difficult_courses−Target))/requested_difficult_meetings) | دو درس دشوار تک‌جلسه‌ای در یک روز و Target=1 → ۱−۱/۲=۰٫۵ |
| PreferredCourses | sum(مدت واقعی جلسه × Willingness/10) / مجموع دقیقه تدریس | ۱۸۰ دقیقه با تمایل ۱۰ و ۹۰ دقیقه با تمایل ۴ → ۲۱۶/۲۷۰=۰٫۸ |

تعداد روزهای واقعی از روزهای متمایز فعالیت همان شخص است. تعداد روز تقویم و کران فاصله ثابت مخفی در الگوریتم نیستند؛ از Context/Policy می‌آیند. اگر کران فاصله صریح در Policy داده نشود، برای هر روز `max(0,آخرین پایان−اولین شروع−۲×کوتاه‌ترین مدت جلسه−۳۰)` جمع می‌شود. برای تقویم پنج‌روزه فعلی `(660−180−30)×5=2250` است. روزی با تنها یک جلسه قابل ارائه، کران صفر دارد. کران صفر در نبود مازاد امتیاز ۱ می‌دهد و تقسیم بر صفر رخ نمی‌دهد؛ کران مثبتِ صریح Policy نیز ممکن است و امتیاز در صفر اشباع می‌شود.

فاصله فقط در همان روز و میان فعالیت‌های واقعی محاسبه می‌شود. زمان بیرون برنامه و میان روزها حساب نمی‌شود. بازه‌های هم‌پوشان ادغام می‌شوند تا کلاس تودرتو شکاف خیالی ایجاد نکند؛ تداخل همچنان مستقلاً در Hard جریمه می‌شود. یک جلسه دوباره برای همان دانشجو ساخته نمی‌شود.

درس دشوار پیش‌فرض DifficultyLevel≥4 است. هر CourseID در هر روز فقط یک‌بار شمرده می‌شود، حتی اگر دو جلسه داشته باشد. مخرج ثابت هر دانشجو، مجموع SessionsPerWeek دروس دشوار درخواست‌شده اوست؛ به‌جای فرض همیشگی «۲ جلسه برای هر درس» از داده می‌آید و در هر جواب با حذف درس تغییر نمی‌کند. اگر هیچ درس دشواری درخواست نشده، مازاد صفر و این مؤلفه برای دانشجوی فعال امتیاز ۱ دارد؛ بدون فعالیت، قاعده دانشجوی غیرفعال مقدم است. این نرمال‌سازی قرارداد آزمایشی ثبت‌شده برای بازبینی معمار است.

## وزن، حالت خنثی و افراد غیرفعال

وزن Preference اهمیت مؤلفه در رضایت شخص است؛ با مقدار مطلوبیت آن مؤلفه یکی نیست. میانگین شخص `sum(weight×component_score)/sum(weight)` است. مثال دو مؤلفه با امتیاز ۱ و ۰٫۵ و وزن‌های ۷ و ۳، رضایت ۰٫۸۵ می‌دهد. وزن صفر در صورت و مخرج اثر ندارد. اگر تمام وزن‌ها صفر یا هیچ ترجیحی ثبت نشده باشد، شخص با score=None و included=False گزارش می‌شود؛ None به معنی «نامربوط/محاسبه‌نشده» است، نه نارضایتی صفر.

- دانشجوی بدون هیچ تخصیص، اگر ترجیح با وزن مثبت دارد، رضایت فردی صفر می‌گیرد و در میانگین دانشجویان می‌ماند.
- استاد بدون جلسه از میانگین استادان حذف می‌شود؛ score=None و reason=inactive_professor. افزودن استاد غیرفعال رضایت را بالا یا پایین نمی‌برد.
- گروه رضایتِ بدون هیچ فرد قابل محاسبه با None گزارش و از ترکیب حذف می‌شود. صفر ساختگی جایگزین نمی‌شود.
- نبود رکورد Preferred برای یک Slot، امتیاز خنثی ۰٫۵ دارد. این مقدار در Policy صریح و قابل نسخه‌گذاری است؛ نه مطلوبیت کامل و نه ممنوعیت. اگر فقط Unavailable ثبت شده باشد نیز این مؤلفه Soft خنثی است، ولی Hard آن حضور را ممنوع می‌شمارد. Preferred با Weight=0 به‌طور صریح مطلوبیت صفر دارد و با وزن صفرِ خود Preference متفاوت است.

## ترکیب نهایی و مرز Hard/Soft

پیش‌فرض طبق آخرین پاسخ کاربر:

```text
SoftScore = RequestCoverage × mean(رضایت گروه‌های قابل محاسبه)
0.5 × mean(0.8,0.9) = 0.425
```

اگر هیچ گروه ترجیح قابل محاسبه نباشد، فقط پوشش درخواست هدف قابل اعمال است و SoftScore=Coverage؛ این به معنی ثبت رضایت کامل برای افراد نیست. اگر هیچ درخواست تأمین نشده باشد SoftScore الزاماً صفر است. نبود هیچ درخواست ورودی با coverage_status=no_input_requests و Coverage=SoftScore=0، جدا از وضعیت معمول گزارش می‌شود.

گزینه تاریخی equal_components نیز تنها با Policy صریح، میانگین Coverage و گروه‌های تعریف‌شده را می‌دهد؛ برای سه مقدار ۰٫۵،۰٫۸،۰٫۹ نتیجه ۱۱/۱۵≈۰٫۷۳۳۳ است. این گزینه تحت تست است اما پیش‌فرض جاری نیست.

Hard و Soft به‌صورت دو نتیجه مستقل در FitnessEvaluation باقی می‌مانند. comparison_key برابر `(hard.total_penalty, -soft.total_score)` است؛ هیچ ضریب بزرگی وجود ندارد. Hard کمتر همیشه مقدم است. هیچ نمره Soft، خطای ساختاری را پنهان یا جواب نامعتبر را معتبر نمی‌کند. خطای ساختاری همان StructuralValidationError فاز دوم است.

## گزارش تفکیکی

SoftEvaluation تعداد درخواست ورودی/تأمین‌شده، Priority کل/تأمین‌شده، پوشش و وضعیت آن، رضایت دو گروه، گزارش تک‌تک افراد و مؤلفه‌های وزن‌دار و score نهایی را دارد. هر PreferenceScore شامل score در [0,1]، weight، raw_value، normalizer و status است. برای هر فرد actual_days، excess_gap_minutes، included و reason نیز وجود دارد. None فقط برای میانگین/شخص حذف‌شده است؛ تمام امتیازهای واقعاً محاسبه‌شده در [0,1] هستند. fingerprint داده و سیاست و نسخه/روش aggregation در خروجی ثبت می‌شوند. هیچ cache یا ورودی پنهانی تغییر نمی‌کند.

## نتیجه آزمون و موارد باز بازبینی

تمام ۱۱۱ آزمون پاس شدند: ۷۴ آزمون قبلی + ۱۰ آزمون Context + ۲۳ آزمون Soft + ۴ آزمون ترکیب. نمونه‌های عددی جدول، مرز ۳۰/۳۱، پوشش صفر/ورودی صفر، وزن صفر، تفاوت استاد و دانشجوی غیرفعال، میانگین Willingness زمانی، مخرج صفر، اشباع، خطای ساختاری، تغییرناپذیری، یک‌باربودن پیش‌پردازش، آزادشدن cache ضعیف، mismatch داده/سیاست و تقدم Hard بررسی شده‌اند. آزمون‌های Loader روی snapshot تأییدشده نسخه مبنا اجرا شدند؛ آزمون‌های جدید مستقل از Excel هستند.

برای بازبینی معمار: neutral_time_score=0.5، مخرج درخواست‌محور توزیع دشوار و حذف گروه رضایت تهی قراردادهای صریح این PR هستند. سیاست coverage_product از آخرین دستور کاربر آمده و با میانگین سه‌گانه قبلی تفاوت دارد. اتصال نتیجه به cache قدیمی خود کروموزوم در این فاز انجام نشده؛ خروجی مستقل و دارای fingerprint است. Runner، جمعیت اولیه و عملگرهای ژنتیک ساخته نشده‌اند. این PR بدون تأیید معماری ادغام نمی‌شود.
