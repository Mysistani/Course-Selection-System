# Phase 5A — Tournament Selection و Course-Based Crossover

ادامه اجرایی در Phase 5B: [Mutation اتمی و Repair محدود](MUTATION_REPAIR.md). شرح پایین محدوده تاریخی فاز 5A است؛ Selection و Crossover همچنان بدون Repair پنهانی باقی مانده‌اند.

این فاز از main ادغام‌شده فاز چهارم شروع شده است. فقط دو ماژول selection.py و crossover.py به موتور اضافه شده‌اند؛ ساختار کروموزوم، Context، Initialization و Fitness تغییر نکرده است. Mutation، Student-Based Crossover، Split/Merge، Repair، Elitism Manager، Evolution Loop، توقف نسل‌ها و UI در این فاز ساخته نشده‌اند. PR و merge طبق دستور جاری با کاربر است.

## API و مثال اتصال

```python
from random import Random
from scheduler.selection import tournament_selection
from scheduler.crossover import course_based_crossover
from scheduler.fitness import evaluate_fitness

rng = Random(55)
parent_a = tournament_selection(population, rng, tournament_size=3)
parent_b = tournament_selection(population, rng, tournament_size=3)
child = course_based_crossover(parent_a.chromosome, parent_b.chromosome,
                               context, rng)
child_fitness = evaluate_fitness(child, context)
```

population می‌تواند PopulationInitialization فاز چهارم یا Sequence اعضای InitializedIndividual آن باشد. Selection خودِ عضو موجود را برمی‌گرداند؛ آن را کپی یا ویرایش نمی‌کند. Crossover فقط Chromosome جدید برمی‌گرداند و ارزیابی مستقل در فراخوانی بعد انجام می‌شود. فرزند به‌طور خودکار وارد جمعیت یا جایگزین فردی نمی‌شود.

امضای APIها:

```text
tournament_selection(population, rng, tournament_size=3,
                     *, allow_mixed_contexts=False) -> InitializedIndividual
course_based_crossover(parent_a, parent_b, context, rng,
                       *, ensure_mixed=True) -> Chromosome
```

## Tournament Selection

نمونه‌گیری با Random ورودی و بدون جایگذاری روی اندیس‌های جمعیت انجام می‌شود. k باید عدد صحیح ۱ تا اندازه جمعیت باشد؛ برای جمعیت خالی، k نامعتبر یا عضو ارزیابی‌نشده خطای روشن صادر می‌شود. پیش‌فرض k=3 است. تمام اعضای ورودی باید FitnessEvaluation داشته باشند. تمام Contextهای جمعیت قبل از مصرف RNG بررسی می‌شوند؛ اختلاف داده یا Policy به‌صورت پیش‌فرض خطاست، حتی اگر عضو Context متفاوت وارد نمونه مسابقه نشود. فقط با allow_mixed_contexts=True صریح این محافظ غیرفعال می‌شود؛ این گزینه برای مسیر عادی یک اجرای GA منظور نیست.

برنده کوچک‌ترین FitnessEvaluation.comparison_key را دارد:

| عضو | Hard | Soft | کلید |
|---|---:|---:|---|
| A | ۰ | ۰٫۱ | (0,-0.1) |
| B | ۱ | ۱٫۰ | (1,-1.0) |
| C | ۲ | ۰٫۹ | (2,-0.9) |

در مسابقه هر سه، A برنده است. اگر Hard برابر باشد، Soft بیشتر مقدم است؛ مثلاً (3,-0.9) از (3,-0.2) بهتر است. در تساوی کامل، rng.choice بین اعضای مساوی بهترین امتیاز انتخاب می‌کند؛ تساوی به عضو اول جمعیت یا اولین نمونه امتیاز ثابت نمی‌دهد.

دو فراخوانی با همان RNG، دو مسابقه مستقل با پیشروی جریان تصادفی‌اند. یک والد ممکن است در هر دو برنده شود و این رفتار ممنوع نیست. API این فاز الزام والد متمایز را به‌صورت مخفی تحمیل نمی‌کند؛ نیاز به والد متمایز باید در قرارداد آینده صریح تعیین شود.

InitializedIndividual ارزیابی اولیه را به‌صورت snapshot نگه می‌دارد. برای جلوگیری از مصرف نمره قدیمی، fingerprint ژنوتیپ اعضای **نمونه‌گیری‌شده** با fingerprint زمان ارزیابی تطبیق داده می‌شود. اگر فرد بعد از ارزیابی تغییر کرده، Selection خطا می‌دهد؛ نه ارزیابی پنهانی می‌کند و نه نمره را بازنویسی می‌کند. Contextها در کل جمعیت بررسی می‌شوند ولی fingerprint فقط برای k نامزد است تا هزینه برابر اسکن کل ژنوم تمام جمعیت نباشد. caller باید پس از تغییر ژنوتیپ، رکورد ارزیابی تازه بسازد.

## CourseBlock و انتقال یکپارچه

هر CourseID یک بلوک شامل همه جایگاه‌های گروه آن درس، فعال یا غیرفعال، تمام SectionGeneها با استاد، اتاق و جلسات، و تمام کلیدهای درخواست همان درس با تخصیص یا None است. برای هر درس دقیقاً یک والد اهداکننده تعیین می‌شود؛ بخش گروه‌ها و بخش انتخاب واحد آن درس هرگز اهداکننده متفاوت ندارند.

مثال: والد A در درس C1 یک گروه فعال و والد B دو گروه فعال دارد. اگر C1 از B انتخاب شود، هر دو گروه فعال و تمام تخصیص‌ها/Noneهای C1 از B می‌آیند؛ جایگاه غیرفعال موجود نیز حذف نمی‌شود. درس C2 می‌تواند همراه تمام گروه‌ها و تخصیص‌های خودش از A بیاید. تعداد گروه فعال دو والد می‌تواند متفاوت باشد ولی مجموعه جایگاه‌ها باید همان مجموعه Context باشد.

ابتدا هر دو والد با validate_structure و Context داده‌شده بررسی می‌شوند. والد نامعتبر با StructuralValidationError و StructureIssueهای اصلی رد می‌شود؛ نام والد نیز به یادداشت خطا اضافه می‌شود. سپس کلیدهای گروه و درخواست یک‌بار در نگاشت‌های موقت برحسب درس دسته‌بندی می‌شوند. CourseIDها، کلیدها و اعضای مؤثر مرتب می‌شوند تا ترتیب Dictionary یا PYTHONHASHSEED روی نتیجه تصادفی اثر نگذارد.

برای هر درس یک سکه اهداکننده با rng.randrange(2) زده می‌شود. پیش‌فرض ensure_mixed=True به این صورت است:

۱. درس‌هایی پیدا می‌شوند که بلوک واقعی آن‌ها در والدها متفاوت است. تفاوت صرف ترتیب فهرست جلسات، تفاوت برنامه محسوب نمی‌شود.
۲. اگر دست‌کم دو بلوک متفاوت وجود داشته باشد ولی همه از یک اهداکننده انتخاب شده باشند، اهداکننده یک درس تصادفی از همان مجموعه عوض می‌شود.
۳. ژن‌ها همچنان کامل از والد مربوط کپی می‌شوند؛ فقط ماسک انتخاب اهداکننده تنظیم شده است. این کار Repair یا Mutation نیست و هیچ ژن ساخته/اصلاح نمی‌شود.

این سیاست به‌معنی سکه‌های کاملاً مستقل یا احتمال برابر برای همه ماسک‌های غیرتک‌والدی نیست؛ قرارداد صریح این نسخه برای فراهم‌کردن مشارکت واقعی هر دو والد است. برای آزمایش سکه‌های مستقل می‌توان ensure_mixed=False داد. در تک‌درسی، والدهای یکسان، یا تنها یک بلوک متفاوت، کپی یکی از والدها خروجی مجاز است؛ تنوع مصنوعی ایجاد نمی‌شود. بلوک‌های خالی یا یکسان برای ادعای مشارکت واقعی استفاده نمی‌شوند.

SectionGeneها با deepcopy به نگاشت موقت جدید منتقل و enrollmentها در نگاشت مستقل ساخته می‌شوند. مقدارهای متن/None و tupleهای جلسات تغییرناپذیرند. Chromosome فرزند فقط یک‌بار ساخته می‌شود؛ در حلقه‌ها assign یا replace_section نداریم. cache فرزند None است و به نمره والد وصل نیست. تغییر بعدی فرزند به والد یا Elite مرجع‌شده سرایت نمی‌کند. validate_structure فرزند هم باید موفق باشد؛ هیچ درخواست، جایگاه یا ارجاع ناقصی ترمیم مخفی نمی‌شود.

## سلامت ساختاری با کیفیت یکی نیست

دو والد می‌توانند هر دو Hard=0 داشته باشند ولی بلوک‌های درس‌هایشان در ترکیب تداخل ایجاد کنند. مثال با استاد P1 و اتاق R1 مشترک و دو گروه ۸نفره با دانشجویان جدا:

| برنامه | C1 | C2 | Hard |
|---|---|---|---:|
| والد A | شنبه T1 | شنبه T2 | ۰ |
| والد B | شنبه T2 | شنبه T1 | ۰ |
| فرزند C1 از A و C2 از B | شنبه T1 | شنبه T1 | ۲ |

فرزند یک تداخل استاد و یک تداخل اتاق دارد، اما ساختارش سالم است و باید بازگردانده شود. Crossover Fitness را محاسبه نمی‌کند، بهبود را تضمین نمی‌کند و جواب بدتر را رد نمی‌کند. تصمیم پذیرش/جایگزینی متعلق به فازهای بعدی است.

## بازتولیدپذیری و مرز Context

RNG حتماً نمونه random.Random ورودی است و RNG سراسری مصرف نمی‌شود. Seed، والدها، ترتیب جمعیت، Context و تنظیمات یکسان در همان محیط Python بازتولیدپذیرند. تست مستقل با PYTHONHASHSEED=1 و 99 و تست وارونه‌سازی ترتیب Dictionary والدها انجام شده است. ترتیب افراد یک Sequence، خود بخشی از ورودی مسابقه است؛ بازچینی جمعیت می‌تواند نمونه تصادفی اندیس‌ها را عوض کند.

Selection از metadata ارزیابی برای جلوگیری از اختلاط Context استفاده می‌کند. Chromosome خام طبق معماری موجود برچسب Dataset/Policy ندارد؛ بنابراین Crossover تنها سازگاری ساختاری والدهای خام با Context مشترک اعلام‌شده را بررسی می‌کند و منشأ Policy آن‌ها را از روی ژن‌ها حدس نمی‌زند. در مسیر عادی، والدها از همان جمعیت ارزیابی‌شده Context مشترک می‌آیند. افزودن provenance به مدل کروموزوم یا نوع عمومی‌تر عضو ارزیابی‌شده برای Evolution Loop آینده، در صورت نیاز تصمیم جداگانه معمار است؛ ساختار فازهای قبلی در این فاز تغییر نکرده است.
