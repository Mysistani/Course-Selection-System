# Phase 5B — Mutation اتمی و Repair محدود

این فاز روی main با SHA پایه `a93f096` شروع شد. داده آزمایشی همان نمونه ناقص یک دانشکده است. هیچ داده یا قانون آموزشی تازه‌ای اضافه نشده است. وضعیت آزمون و آزمایش در [گزارش فاز](PHASE5B_REPORT.md) است. حلقه تکامل، Elitism Manager و رابط کاربری خارج از این فازند.

## API

```python
from random import Random
from scheduler.mutation import (
    MutationSettings, MutationTarget, maybe_mutate, mutate, apply_mutation,
)
from scheduler.operator_support import evaluate_snapshot
from scheduler.repair import RepairSettings, repair_structure, repair_conflicts

rng = Random(55)  # در تمام عملیات همان RNG محلی را ادامه دهید
snapshot = evaluate_snapshot(parent, context)  # یک Hard و یک Soft؛ هزینه با فراخواننده
result = maybe_mutate(parent, context, rng, MutationSettings(), evaluation=snapshot)
# mutate(...) بدون دروازه احتمال، یک عملگر انتخاب می‌کند.
# apply_mutation(..., 'MoveMeeting', MutationTarget(...)) اجرای مستقیم عملگر است.
child = result.chromosome
current = evaluate_snapshot(child, context) if result.report.status == 'applied' else snapshot
repaired = repair_conflicts(child, context, rng, RepairSettings(), evaluation=current)
```

Context از قبل ساخته‌شده را بازاستفاده کنید. `MutationResult` شامل chromosome مستقل و report است. `RepairResult` علاوه بر آن، در مسیر تعارض Snapshot ارزیابی خروجی دارد. ارزیابی در ژن یا cache ذخیره نمی‌شود. Snapshot شامل fingerprint ژنوتیپ و FitnessEvaluation است؛ Snapshot کهنه یا متعلق به Dataset/DesignPolicy دیگر رد می‌شود. بدون Snapshot، Mutation فقط وقتی وارد مسیر هدفمند شود یک مبنا محاسبه می‌کند؛ Conflict Repair یک مبنا محاسبه می‌کند.

## قرارداد اتمی

تغییرات روی دو Dictionary موقت ساخته می‌شوند. `validate_structure` اکنون یک نمای فقط‌خواندنی از نگاشت‌ها را نیز می‌پذیرد؛ API پیشین آن حفظ شده است. تنها پس از اعتبارسنجی، کروموزوم جدید ساخته می‌شود. تعداد دانشجو، واحد و بار استاد همچنان مشتق‌اند. والد/Elite، نگاشت‌ها و cache آنها تغییر نمی‌کنند. رکوردهای SectionGene تغییرناپذیرند؛ خروجی نگاشت مستقل دارد. Cache خروجی None است، حتی در شکست یا عدم تغییر.

موفقیت Mutation حتماً fingerprint متفاوت دارد. شکست اجرای مستقیم، `failed` برای هدف نامعتبر و `not_applicable` برای نبود پیش‌شرط یا اتمام جست‌وجوی محدود است؛ علت ثبت می‌شود. `skipped` صرفاً یعنی دروازه احتمال عبور نکرد. در هر سه حالت خروجی کپی مستقل و ساختاری سالم ورودی است. ورودی ساختاری ناسالم در Mutation/Conflict Repair با StructuralValidationError رد می‌شود و باید به Structural Repair فرستاده شود. HardPenalty صفر لازم نیست؛ هیچ Repair یا رد فرزندِ ضعیف‌تر در Mutation پنهان نیست.

## عملگرها

| عملگر | تغییر و پیش‌شرط |
|---|---|
| MoveMeeting | جابه‌جایی یک جلسه به Slot مجاز و متمایز، تعداد جلسات ثابت |
| SwapMeetings | مبادله جلسه دو گروه؛ بدون جلسه تکراری یا Slot ممنوع؛ جابه‌جایی ترتیب جلسات یک گروه تغییر ژنوتیپ نیست |
| ChangeProfessor | استاد متفاوت با CanTeach=True؛ تک‌گزینه‌ای غیرقابل اعمال |
| ChangeRoom | اتاق متفاوت هم‌نوع و دارای ظرفیت مؤثر کافی برای اعضای فعلی؛ بدون جایگزین آزمایشگاهی ناسازگار |
| SplitSection | جایگاه غیرفعال همان درس، حداقل ۲×MinSectionSize؛ پارتیشن تصادفی معتبر و منابع/جلسات جدید؛ همه تخصیص‌ها دسته‌ای |
| MergeSections | دو گروه فعال همان درس؛ مقصد دارای ظرفیت کل؛ مبدأ کاملاً پاک و غیرفعال |
| ActivateDeactivate | فعال‌سازی با حداقل درخواست بی‌پاسخ واقعی و ظرفیت معتبر؛ غیرفعال‌سازی فقط با بازتوزیع همه اعضا در گروه‌های دارای ظرفیت و حداقل جمعیت |
| MoveStudent | همان درس؛ مبدأ پس از انتقال حداقل جمعیت و مقصد ظرفیت داشته باشند |
| SwapStudents | دو درخواستِ تخصیص‌یافته همان درس در گروه‌های متفاوت؛ تعداد اعضا ثابت |
| AssignUnassign | حفظ کلید درخواست؛ تخصیص None یا تبدیل تخصیص به None؛ رعایت حداقل و ظرفیت گروه متأثر |

MinSectionSize از Context خوانده می‌شود (در داده جاری ۸). ظرفیت مؤثر min(سقف درس، ظرفیت اتاق) است. زمانِ گروه جدید از Slotهای IsAllowed و به تعداد SessionsPerWeek، بدون تکرار انتخاب می‌شود. استاد/اتاق در همه جلسات ثابت‌اند. فعال‌سازی فقط درخواست‌های واقعیِ بی‌پاسخ را می‌گیرد؛ انتقال از گروه فعال متعلق به Split است. برای فعال‌سازی، Priority بیشتر مقدم و تساوی تصادفی است. Deactivate هیچ درخواست را به‌زور حذف نمی‌کند؛ در نبود جای باز شکست می‌خورد. عملگرهای زمان/منبع/SwapStudents نقض‌های سخت موجود را پنهانی رفع نمی‌کنند؛ مرجع ارزیابی همواره Fitness کامل است.

مثال‌های دقیق آزمون: گروه ۱۵نفره تقسیم نمی‌شود؛ ۱۶ نفر به ۸+۸ تقسیم می‌شوند. گروه ۱۶نفره با ظرفیت ۸ قبل از Split جریمه ظرفیت ۸ دارد و در مثال با زمان‌های جدا بعد از آن HardPenalty=0 است. ادغام ۸+۸ در مقصد ظرفیت ۱۵ رد می‌شود و HardPenalty ورودی/خروجی هر دو صفر می‌ماند؛ ظرفیت ۱۶ ادغام را مجاز می‌کند. انتقال از گروه ۸نفره رد و جریمه آن صفر می‌ماند. این اعداد با fixture مستقل از Excel آزموده شده‌اند.

## Settings و انتخاب محدود

`MutationSettings(version='mutation-5b-v1')`: احتمال شروع ۰٫۳۰ فقط در maybe_mutate، احتمال مسیر هدفمند ۰٫۷۰ در mutate، وزن هر عملگر ۱، max_attempts=8 و max_proposals_per_operator=8. وزن صفر عملگر را غیرفعال می‌کند؛ همه وزن‌ها صفر نتیجه روشنِ غیرقابل اعمال دارد. پارامترها قرارداد آزمایشی این فازند.

برای هر عملگر حداکثر ۸ پیشنهاد پیش‌نمایش می‌شود. از عملگرهایی که پیشنهاد قابل اعمال کشف‌شده دارند، با وزن مساوی پیش‌فرض انتخاب می‌شود؛ سپس از پیشنهادهای همان عملگر، عوامل Violation در مسیر هدفمند ترجیح داده می‌شوند. نبود هدف مناسب در عملگر منتخب، مسیر تصادفی و fallback ثبت‌شده دارد. نسبت ۷۰٪ احتمال انتخاب مسیر است، تضمین نسبت مشاهده‌شده در نمونه کوچک نیست. مجموعه عوامل از SectionID، StudentID و استاد/اتاق Violation استخراج می‌شود.

نبود پیشنهاد در بودجه، اثبات ریاضی نبود عملگر در کل فضای جواب نیست. دلایل در unavailable_operations ثبت می‌شوند. کشف پیشنهاد حداکثر تعداد عملگرهای فعال×۸ بار و تلاش commit حداکثر ۸ بار است؛ در apply_mutation جست‌وجوی بدون هدف حداکثر ۸ پیشنهاد و با هدف صریح یک پیشنهاد است. این تعدادها مستقل از تعداد دانشجویان‌اند؛ اسکن داده و کپی نگاشت همچنان هزینه متناسب با اندازه ورودی دارد. جست‌وجو lazy است؛ ضرب دکارتی زوج‌های دانشجو ساخته نمی‌شود. ترتیب کلیدها پیش از تصادفی‌سازی مرتب می‌شود و RNG سراسری دست‌نخورده می‌ماند.

## دو سطح Repair

`repair_structure(c, context, rng, settings, rollback=valid_parent)` با حداکثر ۲۰ تغییر نگاشت، جایگاه‌های مفقود را غیرفعال ایجاد، جایگاه‌های اضافی را حذف، منابع گروه غیرفعال را پاک، شناسه کلید/رکورد را همسان، درخواست مفقود را None و ارجاع نامعتبر را None می‌کند. درخواست ساختگی نمی‌سازد. قصد آموزشی، منابع مفقود گروه فعال یا جلسات خراب را حدس نمی‌زند؛ اگر نگاشت‌ها هنوز ناسالم باشند، تمام تغییرات دور ریخته می‌شوند. rollback باید خود ساختاری سالم باشد. در نبود rollback سالم، نتیجه `failed` و chromosome=None همراه issues است؛ خروجی ناسالم هیچ‌گاه به‌عنوان جواب سالم بازگردانده نمی‌شود. این مسیر Fitness مصرف نمی‌کند؛ اصلاح ساختاری تضمین Hard معتبر نیست.

`repair_conflicts` فقط ورودی ساختاری سالم می‌گیرد. Violationهای مبنا به‌ترتیب موجود و حداکثر ۵۰ مورد بررسی می‌شوند. در هر تعارض از حالت بهترین جوابِ ابتدای همان تعارض، پیشنهادهای زمان/استاد/اتاق/انتقال دانشجو به‌شکل نوبتی ساخته می‌شوند. پیشنهاد باید به عامل Violation مربوط باشد. یک پیشنهاد در همان تعارض می‌تواند چند تغییر قبلی آن تعارض را جایگزین کند، اما تنها در صورت برتری بر بهترین Fitness فعلی پذیرفته می‌شود. هیچ کاندیدای برابر یا بدتر پذیرفته نمی‌شود. در تساوی Hard، افزایش Soft نیز بهبود معتبر است؛ کاهش Hard بر Soft مقدم است. رسیدن به Hard صفر ضروری نیست.

`RepairSettings(version='repair-5b-v1')`:

| بودجه | پیش‌فرض |
|---|---:|
| max_local_candidates: ارزیابی کاندیدا برای هر تعارض | ۵ |
| max_candidate_evaluations: کل ارزیابی کاندیدا | ۵۰ |
| max_candidate_attempts: کل پیشنهاد، حتی نامرتبط/نامعتبر/تکراری | ۱۰۰ |
| max_conflicts: رکورد تعارض مبنا | ۵۰ |
| max_structural_steps: تغییر نگاشت در Structural Repair | ۲۰ |

بودجه صفر مجاز و توقف قطعی است. fingerprintهای تکراری دوباره ارزیابی نمی‌شوند. هزینه مبنا جدا از ۵۰ کاندیداست: بدون Snapshot حداکثر ۵۱ Fitness، با Snapshot حداکثر ۵۰. هر Fitness دقیقاً یک Hard و یک Soft دارد. تلاش‌ها، ارزیابی واقعی مبنا/کاندیدا، تعداد کاندیدای هر تعارض، پذیرش‌ها و Hard قبل/بعد گزارش می‌شوند. rollbacks در Repair شامل پیش‌نویس‌های ردشده و کاندیدای تکراری/برابر/بدتر است؛ پیشنهاد نامرتبط فقط attempt است. در Mutation، پیش‌نمایش کشف، تغییر commit‌شده نیست؛ rollbacks تلاش‌های اجرای ردشده را می‌شمارد. یک rollback لزوماً یک Fitness مصرف نکرده است.

## حدود و تصمیم‌های باز برای معمار

- منشأ Context در مدل فعلی Chromosome ذخیره نمی‌شود. ناسازگاریِ ساختار با Context و Snapshot متعلق به Context دیگر رد می‌شوند؛ دو Dataset با schema یکسان و مقادیر متفاوت، از روی یک کروموزوم خام قابل تشخیص نیستند. افزودن provenance به خود مدل تصمیم معماری جدا می‌خواهد. در اجرای GA باید یک Context ثابت و Snapshotهای متناظر نگه داشت.
- انتخاب از پیشنهادهای کشف‌شده، تخمین محدودِ applicability است. افزایش بودجه، سیاست هدف‌گیری تخصصی‌تر و سهم عملگرها نیاز به آزمایش/تصمیم بعدی دارند؛ این فاز برتری یک سیاست را اثبات نمی‌کند.
- Conflict Repair فقط چهار نوع حرکت دارد؛ مثلاً کسری واحد یا نبود منبع ممکن است با این حرکت‌ها حل نشود. ۱۰۰ پیشنهاد می‌تواند پیش از ۵۰ ارزیابی مصرف شود. هیچ حلقه جست‌وجوی نامحدود یا تضمین حل‌پذیری وجود ندارد.
- Structural Repair محافظه‌کار است؛ در منابع/جلسات فعال خراب، rollback را به حدس‌زدن ترجیح می‌دهد. توسعه دامنه اصلاح نیازمند قرارداد تازه است.

## بازتولید در Windows

از ریشه پروژه در PowerShell:

```powershell
$env:PYTHONPATH = 'src'
python -m unittest discover -s tests -v
python scripts/check_mutation_repair.py
python scripts/check_mutation_repair.py --unconditional --output outputs/MUTATION_REPAIR_5B_UNCONDITIONAL.json
```

گزارش JSON شامل seedها، هش داده/Policy، تمام Settings، ردیف هر فرزند، نوع/وضعیت عملیات، fallback، fingerprint، Hard قبل/بعد، ارزیابی مبنا/کاندیدا، rollback و زمان است. outputs در Git وارد نمی‌شود؛ خلاصه قابل بازبینی در PHASE5B_REPORT نگهداری می‌شود. آزمایش، فرزندان یک جمعیت ثابت را بررسی می‌کند و نسل، جایگزینی یا Evolution Loop ندارد.
